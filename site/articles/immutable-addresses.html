An address that changes with the bytes.

Content fingerprints turn long-lived assets into a smaller coordination problem.

MCMaya ChenOct 02, 20264 min read

Name the representation

A stable URL asks every cache to agree on when its stored representation becomes obsolete. A fingerprinted URL asks a simpler question: has the reader requested the address for this version? When the bytes change, the build emits a new address.

The HTML document becomes the coordination point. It names the current asset, while earlier documents may still name an earlier one. Keep older assets available for a suitable overlap period so a reader with an older document can finish loading it.

Separate document and asset lifetimes

# HTML document
Cache-Control: no-cache

# Fingerprinted asset, such as app.a1b2c3.css
Cache-Control: public, max-age=31536000, immutable

The first response can be stored but must be validated before reuse. The second may remain fresh for a year. The filename must actually correspond to immutable content; adding a hash-looking string without changing it when the bytes change does not provide that property.

Respect framework ownership

Next.js documents its own immutable asset policy and notes that ordinary header configuration cannot override that policy for truly immutable assets. Treat a framework-managed asset path differently from a response your application owns.

These details are version-sensitive. Record your installed framework version when troubleshooting, inspect the headers it actually emits, and consult the matching documentation rather than assuming an older example still describes your deployment.
