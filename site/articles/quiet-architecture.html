The quiet architecture of a faster web.

Freshness, ownership, and the small decisions that make a distributed application feel immediate.

MCMaya ChenOct 18, 20268 min read

Start with the lifetime

The fastest response is often one that does not need to travel. That observation is useful only when the stored representation still answers the question the reader asked. A product price, a release note, and a fingerprinted stylesheet have different lifetimes. Giving them the same policy transfers an architectural decision into an accidental default.

Begin with a short inventory: who owns the representation, who may reuse it, and what event makes it obsolete? These questions establish the boundary between a private browser cache and a shared intermediary. They also make a performance conversation concrete. “Cache more” is an ambition; “allow a shared cache to reuse this public response for sixty seconds” is an implementable decision.

Three directives, three decisions

Names can be misleading. no-cache allows storage but requires successful validation before reuse. no-store tells caches not to store the response. Neither directive purges copies that a previous response already permitted another system to store.

DirectiveStorageReuse condition
no-cachePermittedValidate before reuse
no-storeNot permittedNo new stored response
max-age=60PermittedFresh for 60 seconds
s-maxage=60Shared cachesOverrides max-age there

The distinction matters when the origin is unavailable. A response that requires validation does not become reusable simply because checking it would be inconvenient. Other directives and the actual cache implementation also affect what happens next; the header should be read as a policy, rather than a latency promise.

Make the boundary explicit

A public catalog endpoint can give shared caches a longer lifetime than individual browsers. In this example, a browser receives a zero-second freshness lifetime while an intermediary receives sixty seconds. The stale allowance is separate from freshness.

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=0, s-maxage=60,
  stale-while-revalidate=30
ETag: "catalog-v42"

While the shared response remains fresh it may be reused. After it becomes stale, a supporting cache may serve it for another thirty seconds while attempting revalidation. This does not guarantee a background request at a particular instant, and it does not make a browser use s-maxage. Inspect your provider’s behavior as well as the protocol semantics.

Immutable means a new address

A content hash in an asset filename gives a long cache lifetime a reliable foundation. Changing the bytes changes the URL. Keep the HTML document on a shorter policy so it can point to the new asset. Long freshness without a versioned address can leave a perfectly functioning cache serving an obsolete release.

Frameworks also reserve decisions. Next.js documents a year-long immutable policy for truly immutable assets, including static image imports with hashed filenames; that policy cannot be overridden through its ordinary headers configuration. This is a framework rule, not a universal statement about every HTTP response.

Measure at both boundaries: the response leaving the origin and the response delivered to the reader. An intermediary can add, transform, or consume headers along the way.

Observe before extending

Record response headers, request conditions, and the age of the stored representation before interpreting a timing graph. A lower median may hide an origin that receives a burst of simultaneous validations at expiry. A high hit ratio may hide responses that should never have been shared.

A useful rollout changes one lifetime at a time and preserves a way to compare representations. The result should be a clear explanation of why a given response is reusable.
