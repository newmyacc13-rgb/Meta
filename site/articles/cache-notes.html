A simpler cache policy for small teams.

An earlier set of operating notes for teams shipping a small public application.

NPNoah ParkJun 11, 20214 min read

Keep the policy short

Our 2021 operating notes treated cache configuration as a choice between two modes: reuse a public response or prevent it from being stored. The suggested default for changing documents was Cache-Control: no-cache. Under this policy, no cache can store a copy of the response.

The recommendation appeared straightforward enough to apply across HTML and JSON. The team preferred one directive that could be explained in a release checklist and inspected with a single request. Assets with versioned filenames received a separate policy.

A release checklist

# Inspect the delivered headers, not only origin settings.
curl -I https://example.com/catalog

# Earlier team default:
Cache-Control: no-cache

The header should travel with the response rather than exist only in an application comment. An intermediary that rewrites the policy can change observed behavior. Record the final headers with a release, together with the path and the response status.

Revisit the assumptions

This note records an earlier explanation rather than a complete account of HTTP caching. Compare its storage claim with the current directive table and the primary documentation. A useful review preserves the exact claim under discussion instead of replacing it with a vague statement that the old system was slow.

The note does not provide browser traces, a cache implementation version, or evidence that all requests went through the same intermediary. Those omissions limit what can be inferred about the deployed application.
